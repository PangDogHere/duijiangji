# 对讲机 · PTT Walkie-Talkie

基于 [Rendezvous](https://github.com/predatorray/rendezvous) 的「无服务器 WebRTC」思路改造的安卓对讲机 App。

> 原项目是视频会议；这里砍掉视频，保留其 **PeerJS 信令 + 6 位频道码 + 中继台统筹** 的骨架，
> 换成 **PTT 按住说话** 的半双工语音。

**当前版本：v1.4**（公共大厅：打开 App 就能发现 —— 不再受 WiFi 限制，详见文末变更记录）

---

## 一、装到手机

1. 把 `对讲机-v1.4-debug.apk` 传到安卓手机（微信 / 数据线 / 网盘都行）
2. 点击安装。系统提示「未知来源应用」时，允许即可（这是未上架签名的调试包）
3. 首次打开会申请**麦克风权限**，必须允许，否则说不了话

> 最低支持 Android 6.0（API 23）。覆盖安装老版本即可，不用先卸载。

## 二、怎么用

**一台手机当「中继台」（创建频道），其他手机加入同一个频道。**

1. **台长**：填呼号 → 点「📡 创建频道」→ 频道码留空就自动生成，也可以自己填一个好记的
2. **成员**：填呼号 → 输入频道码 → 点「🔊 加入频道」
3. **说话**：**按住底部大圆钮说话，松开收听**。同一时刻只有一个人能讲（半双工，和真对讲机一样）
4. 频道被别人占用时按钮显示「频道占用」，继续按住会自动排队，对方一松手就轮到你
5. 中继台离开 = 频道解散

> 说明文字都收在右上角的 **ⓘ** 按钮里（速上手 / 音质 / 回音 / 原理 / 限制），首页只留必要的操作。
> 版本号显示在首页标题下方。

### 自定义频道码（v1.3 新增）

首页的「频道码」输入框就是给这个用的：

| 你想做的事 | 怎么操作 |
|---|---|
| 用自己好记的码（如 `888666`、`NEARBY`） | 直接填进去 → 点「创建频道」 |
| 让系统给你随机生成一个 | 输入框留空 → 点「创建频道」 |
| 手气不好想换一个随机的 | 点输入框右边的 **🎲** |
| 加入别人的频道 | 填码 → 点「加入频道」 |

- 只允许 6 位**字母或数字**，小写会自动转成大写、非法字符自动过滤
- 自己指定的码如果**已被别人占用**，会明确告诉你并退回首页让你改 —— 不会偷偷换掉
- 留空时创建，会沿用你上次自己开的那个码，团队的频道码因此固定，不用每次重发

### 打开 App 就发现频道（v1.4 重点）

**不用问频道码、不用输任何东西 —— 只要有人在开频道，你打开 App 就能看到。**

首页会自动列出「可连接频道」卡片，每条左边带一个来源标签：

| 标签 | 含义 | 需要什么条件 |
|---|---|---|
| **附近** | 和你在**同一个 WiFi** 的同伴（局域网广播发现） | 同一 WiFi，且路由器没开「AP 隔离」 |
| **在线** | 通过**公共大厅**发现的同伴（跨网络） | 双方都能上网（4G / 任意 WiFi 都行） |

- 发现新频道时会有**预警横幅**（绿框 + 震动 + 倒计时收起），点「**一键加入**」直接进去
- 还没发现东西时，首页显示「正在搜索可连接的频道…」，让你知道它在找
- 点卡片里任意一条即进，**全程不碰频道码输入框**

> **两种来源自动合并**：同一个频道如果既在局域网听到、又从大厅推过来，只显示一条并标「附近」（更近更准）。

不想被 / 不想扫：**⚙ 设置 → 频道发现**（三个开关，默认都开）。

#### 「公共大厅」是什么？为什么可以不用服务器？

不同网络的设备之间 UDP 广播根本到不了，想互相发现**必须有一个公共会合点**。这个 App 的做法是复用它在用的 PeerJS 公共 broker：

- **约定一个固定 id 当「大厅」**，谁先打开 App 谁自动当选大厅
- 其他人的 App 一打开就挂上去：上报自己的频道、接收在线频道列表
- 大厅掉了（当选那台手机关掉 / 息屏），其他人会**自动重新选一个**，你无需任何操作
- 全程**没有任何自建服务器**，也不花一分钱

> ✅ 打开 App 就能发现 —— 同 WiFi 标「附近」，跨网络标「在线」
> ⚠️ 完全断网（飞行模式）时「在线」用不了，但「附近」照旧
> ⚠️ 频道码依然有用：不想被公开的频道，把「允许别人发现我的频道」关掉即可

## 三、语音质量（v1.3 重点）

### 先说清楚 VoNR 这件事

**VoNR(Voice over New Radio) 是 3GPP 定义的 5G 原生语音方案**，由运营商核心网实现
（IMS + EVS 编解码 + 5QI=1 的专用 QoS 承载），**App 层没有任何办法"实现 VoNR"** ——
那需要运营商网络配合，不是一个 APK 能做的事。

但它的**质量设计原则是可以照搬的**，这版就按这五条做了取舍：

| VoNR / EVS 的做法 | 本 App 的等效实现 |
|---|---|
| EVS 全带宽编解码（音频带宽最高 20kHz） | 锁定 **Opus 全带宽 48kHz 单声道**，并把 Opus 强制排到编解码列表第一位 |
| 信道编码冗余抗丢包 | Opus **带内 FEC**（`useinbandfec=1`）：丢包时用冗余数据补齐，而不是直接卡顿 |
| 低速率舒适噪声，不做粗暴静音 | **关闭 DTX**（`usedtx=0`）：避免每句话的起头被静音检测削掉 |
| 编码速率充足（13.2~24.6kbps 已透明） | 按档位给 **20 / 40 / 64 kbps**，宽带参数约束住下限 |
| 专用 QoS 承载，不被别的业务挤占 | 通话期间**独占音频焦点**（原生 `USAGE_VOICE_COMMUNICATION`），别的 App 通知音插不进来 |

### 顺带修掉的一个大坑

WebRTC 里 **编解码是协商出来的**。如果协商到 `PCMU`/`PCMA`，那就是 **8kHz 电话音质** ——
听起来"闷、糊、像在桶里"，这是"通话质量不好"最常见的真凶。
本版把 Opus 钉死在列表首位，并在诊断面板把**实际协商到的编解码**显示出来（必须是 `audio/opus`）。

### 音质档位

频道页的「🎚 标准」可以循环切换：

| 档位 | 码率 | 什么时候用 |
|---|---|---|
| 省流 | ~20 kbps | 信号差、卡顿频繁时 |
| 标准 | ~40 kbps | 默认，多数场景的最优解 |
| 高保真 | ~64 kbps | 网络好、想听得更清楚时 |

> 不是码率越高越好。弱网下盲目冲高码率会更容易丢包，反而更糊。
> 旁边的「网络 优/良/差」是**实时链路评分**（延迟 + 抖动 + 丢包 + 编解码 综合），掉到"良"就该考虑降档或换个位置了。

## 四、听到回音怎么办

**先说结论：这不是 App 的 bug，是物理现象。**

两台设备放在同一个房间、都开外放时，必然形成这样一个循环：

```
A 说话 ──► B 的喇叭放出来 ──► A 的麦克风又收进去 ──► 传回 B ──► B 听到"回声"
   ▲                                                              │
   └──────────────── 如此往复，延迟叠加，回音越来越明显 ◄──────────┘
```

真正的对讲机同屋测试也会这样。回音轻重取决于：**两台设备的距离、外放音量、网络延迟**。

### 怎么消除

| 做法 | 效果 |
|---|---|
| **戴耳机** | 最彻底，回音直接消失 |
| 两台设备**拉开 2 米以上**，别放同一张桌子 | 明显减轻 |
| 频道页点「**回音?**」→「一键压回音」 | 自动切听筒 + 音量降到 60%，喇叭漏音降 20~30dB |
| 频道页手动拖**音量**滑杆（建议 50~70%） | 降低环路增益 |
| 点「🔊 外放 / 👂 听筒」切换输出 | 听筒模式漏音极小 |

### 想确认是不是这个原因

把其中一台设备拿到**另一个房间**再试一次。回音若消失，就是这个原因，没有别的可能。

> 在本机用两个真实 Chrome 做过逐帧测量（`echo_probe.mjs`），软件侧完全干净：
> 对方说话时本机麦克风确实是关的（发送音频能量 = 0），本机也从不播放自己的声音（播放电平 = 0）。

RTT、抖动、丢包率，以及附近发现的运行状态。截图发出来就能直接定位。

## 六、工作原理

| Rendezvous 原设计 | 本 App |
|---|---|
| PeerJS 公共 broker 只做信令 | 一样，零部署 |
| 6 字母会议代码 | 一样，6 位频道码（去掉易混淆的 I/L/O/0/1） |
| 主持人统筹全场 | **中继台**：注册频道码、维护成员表、仲裁发言权 |
| 主持人离开 → 会议结束 | 一样 |
| 纯静态、无后端 | 一样，网页打包进 APK，离线可用 |
| 主持人**转发媒体流** | ⚠ **改为成员间 P2P 直连**（见第七节） |
| WebRTC 音视频流 | 只留音频，用 `<audio srcObject>` 播放 |
| — | **局域网 UDP 广播**做频道发现（v1.3） |
| — | **公共大厅**做跨网络频道发现，复用同一个 broker（v1.4） |

```
       台长 (HOST)                    发现层（与语音无关，互不干扰）：
      /            \            实线 = 语音 P2P 直连        ┌─ 局域网 UDP 广播 → 「附近」
   成员甲 ──────── 成员乙        虚线 = 与中继台的数据连接    └─ 公共大厅（自组织）→ 「在线」
   \____________/               （仅信令）
        │                       另：台长每 2 秒向局域网广播一次频道信息
        └─ 频道码 / 成员表 / 发言权仲裁
```

**频道发现是独立的一层**，不影响语音链路：局域网广播负责同网发现（快、准），
公共大厅负责跨网发现（广、靠 PeerJS broker 自组织），两个来源合并成一个列表。

**半双工四道保险**：

1. **源头门控**：没拿到发言权，本地麦克风 track 恒为 `enabled=false`
2. **中继台仲裁**：唯一的发言权裁判，同一时刻只授权一个人
3. **即时退让**：一旦收到「你被排队」的通知，立刻闭嘴，不等下一个广播包
4. 附加：自己按住说话时本地**不播放远端**（真对讲机听感，也切断对方尾音被自己麦克风再采一遍）

## 七、架构取舍（为什么没照搬"中继台转发"）

原文章的核心是**主持人中转媒体流**（星型）。照搬实现后，实测在手机上**全程静音**：

> Chrome 里 `AudioContext.createMediaStreamSource(WebRTC 远端流)` 在默认 **44100Hz** 下输出恒为 0
> —— WebRTC 音频是 **48000Hz**，这条重采样路径失效。
> 独立实验验证：44100Hz 读远端流 = 静音；48000Hz 读 = 正常；读本地流 = 正常。

星型转发必须依赖这个 API 才能把发言者声音"混"给其他人，所以直接换掉：

| | 中继台转发（原设计） | P2P 全互联（现方案） |
|---|---|---|
| 播放路径 | Web Audio 路由（有静音风险） | `<audio srcObject>`（WebRTC 标准做法） |
| 成员带宽 | 每人 2 条流（上行+下行） | 每人 N-1 条流 |
| 适用人数 | 可扩展 | ≤ 8 人很稳 |
| 任意两人 NAT 不通时 | 只要都能连中继台就没事 | 那两人互相听不到 |

对讲机的典型场景（同一现场 / 同一 WiFi，几个人）下，全互联是更快、更可靠的选择。

## 九、已知限制

- **没有后台保活**：切后台或锁屏，WebView 会被系统降频/冻结，语音会断。想真正「息屏对讲」需要加前台 Service
- **需要任意两人之间能直连**：极端 NAT 环境下可能连不上。当前只配了 STUN 没有 TURN
- **「在线」标签需要能上网**：完全断网（飞行模式）时收不到，但「附近」标签靠局域网广播，不受影响
- **公共大厅由用户手机临时担任**：全部人同时关掉 App，大厅会消失（再有人打开就立刻重建）。实测三端会收敛出唯一大厅，持有者退出后剩余端能自愈接任 —— 见 `lobby_test.mjs`
- **同屋外放必有回音**：物理限制，App 只能改善不能根除，见第四节
- **调试签名**：现在是 debug 包，能装能用但没正式签名，不能上架

## 变更记录

### v1.3 → v1.4

**用户反馈**：突破已知限制 —— 只要打开 App 就能发现。

**核心：公共大厅（自组织频道目录）**

v1.3 的发现只在同一个 WiFi 内有效，跨网络（一人 4G、一人 WiFi）看不到。根因是物理的：
UDP 广播出不了网段，跨网络发现**必须有公共会合点**。

于是把 App 本来就在用的 PeerJS 公共 broker **复用成「频道大厅」**：

- 约定固定 id（`pangou-wt-lobby-v1`），**谁先打开 App 谁自动当选大厅**，其余端挂上去
- 大厅维护在线频道表（只有「台长 + 允许被发现」的频道才进目录），有变化时广播给所有客户端
- **双向心跳 + 失联判定**：客户端 5s 一次心跳，15s 没收到任何回音就判定大厅已死 → 退避后重新竞选
- 大厅侧靠心跳超时清理僵尸条目；目录没变化时不广播，避免刷屏

**踩到的坑（重要）**：起初只监听 DataConnection 的 `close` 事件判断大厅掉线，
结果**关掉大厅那台设备后其余端 75 秒都不接任** —— 因为对端页面被直接关掉时，
WebRTC 的 close 事件要几十秒才触发，根本来不及自愈。改成「心跳回执 + 超时判定」后恢复正常。

**界面**

- 首页新增「可连接频道」来源标签：**附近**（同一 WiFi）/ **在线**（公共大厅，跨网络）
- 两个来源自动合并，同一频道优先标「附近」

### v1.0 → v1.1

**症状**：按住 PTT 按钮界面正常变绿、成员列表也显示"正在讲话"，但对方完全听不到声音。

**定位过程**：用 Playwright 拉起两个真实 Chrome + 合成麦克风互讲，在链路每个节点实测电平：

```
台长自己的声音进广播总线 : peak 1.007   ✅ 正常
台长发出的音频字节        : tx 10187    ← 在发
成员收到的音频字节        : rx 10187    ← 收得到！网络层完全通
成员播放入口电平          : peak 0      ❌ 断在这里
```

**根因**：`AudioContext.createMediaStreamSource(WebRTC 远端流)` 在默认 44100Hz 的
AudioContext 下输出恒为静音（WebRTC 是 48000Hz，该重采样路径失效）。中继台转发架构
整个建立在这个 API 上。

**修复**：改掉不可靠的环节 —— 语音改走成员间 P2P 全互联，用 `<audio srcObject>`
直接播放远端流；半双工改由**源头麦克风 track 门控**实现。
